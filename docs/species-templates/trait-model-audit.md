# Trait model audit (independent per-trait percents, ratified 2026-09-02)

Adversarial read-only pass over every file the trait-model change touches, looking for statements that still assume the retired count-and-draw model, semantic knock-on effects, script logic errors, record inconsistencies, and gaps a generator implementer would have to guess at.

**Verdict: the change is sound and internally coherent where it was applied, but it was applied to the ratifying paragraphs only. The surrounding prose, both worked walkthroughs, both schema documents, and the sample record still teach the old model, and one ratified platform rule ("rares roll more, never better") is now unenforceable rather than merely stale.** One genuine rule break, four contradictions, two script defects, one record inconsistency, and six under-specified areas.

Severity key: **BREAKS** = a ratified rule no longer holds under the new model. **CONTRADICTS** = the text states the retired model as current and would mislead an implementer. **STALE** = written under the old model, harmless because superseded text is nearby or the statement survives rewording. **AMBIGUOUS** = the change leaves a decision an implementer must guess.

## Answers to the specific questions asked

**Does independent rolling break "the standard must never be better than the rare"?** Yes, as a per-individual guarantee — see #1. The old model enforced it structurally: every individual got the `guaranteed` set, and the pool only ever added on top, so no classic could be missing its species identity and no classic could out-trait a rare. Independent rolling preserves the first half (body-demanded traits at 100 still appear on every individual) but loses the second: trait count is now a random variable whose realizations overlap heavily across the population, so a common individual routinely carries more traits than an individual holding a single-digit rare. The fix is not to restore the cap; it is to stop treating count as a rarity signal and grade traits by inverse percent instead. That is a design ruling for Nick.

**Do the tilts still make sense as multipliers?** Not at the boundaries — see #15. A 100 is immune to upward tilt and vulnerable only to downward tilt, which quietly breaks the "every individual carries it" contract for body-demanded traits; a 2 is effectively immune to both because integer percents cannot express the change. Multipliers were scale-free under a weighted draw and are not under absolute percents. Recommend either exempting 100 from tilts entirely or moving tilts to logit space.

**Is "roll higher first" well-defined when both partners are tilted?** No — see #11a. If tilts are applied before ordering, the order depends on the individual's rolled attributes (charisma tilts the two partners in opposite directions by design), so the same species produces different exclusion semantics for different individuals, and the validator's authored-percent tie check does not correspond to anything at generation time. The design must state explicitly that ordering is fixed by the authored percent and tilts apply only to the chosen roll's probability. That is one sentence and it is currently missing.

**Does anything downstream depend on a bounded trait count?** Ability assembly does not (#26). The record shape does, in the sense that its `guaranteed`/`rolled` split has no meaning any more (#14). Temperament rolls last and is tilted by "the rolled body" (`:231`) — the doc never says trait *count* feeds temperament, only that traits roll before it, so no break, but if any tilt formula was going to read trait count it now reads an unbounded value. The platform rarity model does depend on it and breaks (#1). The duel derivation sketch reads traits individually and would simply stack more of them (#17).

**Are the converted records consistent?** The JSON files are both valid under the new model and under the script. Their walkthroughs are not: both still argue the old model in their reasoning sections with only an appended changelog line reconciling them (#12, #13), Tetrahive's walkthrough table lists a trait the JSON does not carry and inverts two others against its own "kept their relative order" claim (#13a, #13b), and Graviclaw silently dropped `nocturnal` (#12). Neither walkthrough justifies its percents, which the skill requires.

## Recommendations, in priority order

1. **Get a ruling on #1 and #14 before anything else.** The rarity question ("does count still mean anything?") and the record shape question ("what replaces `guaranteed` vs `rolled`?") are the two that block implementation, and neither can be resolved by editing. Everything else is downstream of them.
2. **Fix the two script defects (#10, #11) and the skill wording that mirrors them (#18) in one pass**, since the `mind`/`manipulation` predicates and the exclusion ordering are the same underlying question: does a rare pool entry count, or only a 100? Right now the script is stricter than the model and will deny correct templates.
3. **Rewrite rather than append.** Items 6 and the template-format block in the design doc (#3, #4), both schema documents (#2, #6, #7, #8), and both walkthroughs (#12, #13) should be edited in place. The current pattern of leaving the old ratified paragraph and adding a superseding one 65 lines later has already produced one incoherent piece of reasoning in a shipped walkthrough (`graviclaw.md:62`), and the template-format block actively teaches four validation failures.
4. **Specify the tilt algebra (#15) and the exclusion-ordering rule (#11a) as normative sentences in section 6.** Both are single sentences and both are currently guesswork for the implementer.
5. **Regenerate `sample-record-graviclaw.json` (#9) once #14 is ruled**, and re-run the blind-record audit against it — the current pilot record now tests a superseded schema.
6. **Revisit the 3.5 expected-count warning (#16)** with a real target distribution, or delete it; it is the last artifact of the retired cap and it currently encodes a bound the ruling explicitly abolished.
